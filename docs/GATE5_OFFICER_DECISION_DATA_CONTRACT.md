## 1. Decision Contract Specification

Every evacuation decision generated by JalRakshak must strictly adhere to the following schema. All fields are mandatory and machine-readable.

| Field Name | Type | Format / Constraints | Description |
|:---|:---|:---|:---|
| `decision_id` | `string` | Unique identifier `dec-<scen>-<ts>` | Unique audit identifier for the decision |
| `scenario_id` | `string` | e.g. `scen-tehri-001-baseline` | Underlying hydraulic breach scenario identifier |
| `hydraulic_artifact` | `string` | e.g. `tehri_dam_break.p01.hdf` | HEC-RAS hydraulic output file name |
| `hydraulic_artifact_sha256` | `string` | 64-hex SHA-256 | Cryptographic checksum of the HEC-RAS result |

| `origin` | `string` | e.g. `Malidewal Lowland Village` | Human-readable name / ID of evacuation origin |
| `destination` | `string` | e.g. `Chamba High-Ground Relief Shelter` | Human-readable name / ID of relief shelter |
| `route_id` | `string` | e.g. `Route A (N-MALIDEWAL -> ...)` | Identifier of the selected primary route |

| `provenance` | `object` | Key-value dictionary | Full audit trail linking to HEC-RAS outputs |

## 2. Route-Level Decision Status Definitions

The system uses mathematically rigorous, mutually exclusive status definitions:

### 2.1 `FEASIBLE`
- **Definition:** For every edge $e_i$ along the route, clearance occurs strictly before flood arrival with the safety buffer included, and the available departure time margin exceeds the configured low-margin threshold ($M_{\text{th}} = 5.0\text{ min}$):
$$\forall e_i \in \text{Route}: \quad D_{\text{departure}} + T_i + B < A_i \quad \land \quad \text{Margin} > M_{\text{th}}$$
- **Officer Terminology:** "FEASIBLE UNDER THE SELECTED SCENARIO AND CONFIGURED RULES."

### 2.2 `LOW MARGIN`
- **Definition:** The route is feasible, but the remaining margin before the deadline is narrow ($0 \le \text{Margin} \le M_{\text{th}}$):
$$0 \le \text{Margin} \le 5.0\text{ min}$$
- **Officer Terminology:** "FEASIBLE WITH LOW TIME MARGIN (< 5 min)." Must NEVER be labeled as `SAFE` or `CLEAR`.

### 2.3 `INFEASIBLE`
- **Definition:** At least one edge $e_i$ experiences flood inundation before the evacuating vehicle can clear it:
$$\exists e_i \in \text{Route}: \quad D_{\text{departure}} + T_i + B \ge A_i \quad \implies \quad \text{Margin} < 0$$
- **Officer Terminology:** "ROUTE INFEASIBLE: Projected flood arrival precedes vehicle clearance."

### 2.4 `DATA GAP`
- **Definition:** Hydraulic arrival data or road geometry is missing or unmapped for one or more edges:
$$\exists e_i \in \text{Route}: \quad A_i = \text{NULL / UNMAPPED}$$
- **Officer Terminology:** "DATA GAP: Route feasibility cannot be determined due to missing hydraulic exposure data."

### 2.5 `NO_FEASIBLE_ROUTE`
- **Definition:** No candidate path between Origin $O$ and Destination $D$ has status `FEASIBLE` or `LOW MARGIN` (or the graph is disconnected).
- **Officer Terminology:** "NO FEASIBLE ROUTE: All evaluated candidate paths are infeasible or blocked."

## 3. Road-Level Status Definitions

| Status | Mathematical Rule | Physical Meaning |
|:---|:---|:---|
| **`OPEN`** | $h_{\text{max}} < 0.30\text{ m} \land v_{\text{max}} < 1.0\text{ m/s}$ | Road remains completely dry or below vehicle hazard threshold |
| **`AT_RISK`** | $h_{\text{max}} \ge 0.30\text{ m} \land t_{\text{sim}} < A_i$ | Road will be inundated at time $A_i$, currently accessible |
| **`INUNDATED`** | $h_{\text{max}} \ge 0.30\text{ m} \land t_{\text{sim}} \ge A_i$ | Floodwaters have reached or exceeded the critical threshold |
| **`DATA_GAP`** | Road edge outside 2D mesh domain or missing hydraulics | Hydraulic exposure cannot be established |

## 4. Absolute Language Policy

- **Prohibited Words:** `SAFE`, `GUARANTEED`, `CERTAIN`, `ZERO RISK`, `100% ACCURATE`, `FIELD VALIDATED`.
- **Mandatory Disclosures:** Every response must state that travel times use static engineering speeds and physical validation against historical breach events is not established.
